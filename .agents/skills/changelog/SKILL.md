# Changelog discipline for nesdit

`CHANGELOG.md` follows [Keep a Changelog](https://keepachangelog.com/en/1.0.0/).
It has one `## [Unreleased]` section at the top and one immutable section per
release. Historical sections generated by the earlier release-please setup
keep their original format; everything from `## [Unreleased]` downward uses
the format below. The rule: **a user-facing change and its changelog bullet
land in the same commit.** Do not batch notes for later; later never comes.

## Writing entries

- Add bullets under `## [Unreleased]` using the standard subsections:
  `### Added`, `### Changed`, `### Fixed`, `### Removed`. Create the
  subsection if it does not exist yet; keep subsections in that order.
- One bullet per user-visible change, present tense, backticked identifiers:
  `* Add local MessagePack inspection with \`--input-codec msgpack\``.
- Belongs in the changelog: CLI surface changes — new or changed flags and
  flag values (`--input-codec`, `--to`, `--bfbs`, `--nats-codec`, …);
  inspection, conversion and fidelity contracts; resource limits and budgets;
  new or reworded failure diagnostics and exit codes; platform support;
  packaging and installation behavior (`make install`, hooks); dependency
  switches; security fixes.
- Does not belong: pure internal refactors with no observable CLI behavior
  change, test or fixture churn, benchmark bookkeeping, formatting, typo-level
  doc fixes. When unsure, one short line under `### Changed` beats silence.
- Public-facing text rules apply: no private ticket IDs, planning/tracking
  metadata or workstation paths in bullets.

## Creating CHANGELOG.md entries from history

When backfilling (e.g. after a large landed batch), reconstruct entries from
`git log` commit subjects and bodies of the merged work, one bullet per
user-visible change, grouped under the correct subsection. Verify each bullet
against the diff (`git show --stat`) — commit subjects alone are leads, not
evidence. Keep bullets about what a CLI user observes, not how it was built.

## Cutting a release

Never hand-edit version numbers, tags or release assets yourself:

```bash
make bump-version            # auto-detects from commit subjects; or BUMP=patch|minor|major|x.y.z
```

`scripts/bump-version.sh` edits `VERSION` only — it commits and tags nothing.
The release flow is `make release-cli`: it commits the VERSION bump itself
(`chore: bump version to x.y.z`), runs the mandatory full gate
(`make test-all`), packages the three release targets, creates and pushes the
annotated `vX.Y.Z` tag, and publishes the GitHub release with assets. See
`docs/releasing.md` for prerequisites, permissions and partial-upload
recovery.

The changelog steps around a release:

1. Before or together with the release, rename `## [Unreleased]` to
   `## [x.y.z] - <today>`, insert a fresh empty `## [Unreleased]` above it,
   and commit that change (with any availability-docs updates).
2. Never rewrite, reorder or backdate historical release sections.
3. Version semantics: new capabilities or CLI surface = minor; fixes and
   refinements = patch; changes that remove or redefine existing flags or
   behavior = major.
